### Модель User

Создана модель `models/User.js`:

| Поле | Тип | Требования |
| --- | --- | --- |
| id | INTEGER | Primary key, auto increment |
| name | STRING | Обязательное |
| email | STRING | Обязательное, уникальное |
| password | STRING | Обязательное, хранится только hash |
| role | ENUM('user', 'admin') | По умолчанию `user` |
| lastLogin | DATE | Дата последнего входа |
| createdAt / updatedAt | DATE | Создаются Sequelize автоматически |

При регистрации роль берётся только из значения по умолчанию. Даже если вручную отправить поле `role=admin`, контроллер его не использует, поэтому пользователь не может сам стать администратором.

### Переменные окружения и сессии

В файл `.env` добавлены `SESSION_SECRET` (длинная случайная строка) и `BCRYPT_ROUNDS=10`. Файл `.env` указан в `.gitignore`. Если `SESSION_SECRET` не задан, приложение не запускается и выводит сообщение.

Сессия подключена в `app.js`:

```js
app.use(session({
    secret: process.env.SESSION_SECRET,
    resave: false,
    saveUninitialized: false,
    cookie: {
        maxAge: 1000 * 60 * 60,
        httpOnly: true
    }
}));
```

`resave: false` — сессия не сохраняется повторно, если не изменилась. `saveUninitialized: false` — для гостей сессия не создаётся. Cookie живёт один час, `httpOnly` запрещает читать её из JavaScript на странице.

После входа в сессии сохраняются только `id`, `name`, `email` и `role`. Пароль в сессию не попадает. Содержимое `req.session.user` и ID сессии показаны на странице профиля в блоке «Данные сессии».

### Маршруты аутентификации

Маршруты находятся в `routes/authRoutes.js`, логика — в `controllers/authController.js`:

| Метод | URL | Назначение |
| --- | --- | --- |
| GET | `/register` | Форма регистрации |
| POST | `/register` | Создание пользователя |
| GET | `/login` | Форма входа |
| POST | `/login` | Проверка данных и вход |
| POST | `/logout` | Завершение сессии |
| GET | `/profile` | Профиль пользователя |

**Регистрация.** Форма содержит имя, email, пароль и подтверждение пароля. Проверяется, что все поля заполнены, имя не короче двух символов, email корректный и ещё не зарегистрирован, пароль не короче шести символов и совпадает с подтверждением. При ошибке пользователь не создаётся, над формой выводится список ошибок, а поля пароля остаются пустыми. Если email уже занят, возвращается код 409.

Перед сохранением пароль хэшируется:

```js
const rounds = Number(process.env.BCRYPT_ROUNDS) || 10;
const hashedPassword = await bcrypt.hash(req.body.password, rounds);
```

В базе хранится только hash вида `$2b$10$...`. Пример содержимого таблицы:

```sql
SELECT id, name, email, role, password FROM "Users";
```

```
 id |   name    |       email       | role  |                           password
----+-----------+-------------------+-------+--------------------------------------------------------------
  1 | Petr User | user@example.com  | user  | $2b$10$9DBc2BYbByLYiJdW/GbZneq66OeJzOtc.pZ7tHlAefIuZYpWEWp5y
  2 | Admin     | admin@example.com | admin | $2b$10$z6LVSZch5mEl0xiOignoFuGN8Tdsxonia5lVzrLVf67EG0iTiD2r6
```

**Вход.** Пользователь ищется по email, пароль проверяется через `bcrypt.compare()`. При успехе обновляется поле `lastLogin`, в сессию записываются данные пользователя и выполняется переход на `/profile`. Если пользователь не найден или пароль неверный, выводится одно общее сообщение «Неверный email или пароль» (код 401), чтобы нельзя было узнать, существует ли email.

**Выход.** Выполняется только методом POST (кнопка «Выход» в меню — это форма). Сессия удаляется через `req.session.destroy()`, cookie очищается, пользователь перенаправляется на `/login`. Запрос `GET /logout` возвращает 404.

**Профиль.** Страница `/profile` показывает имя, email, роль, дату регистрации и дату последнего входа. Пароль и его hash не выбираются из базы (в запросе явно указаны нужные поля).

### Middleware аутентификации и авторизации

В `middleware/auth.js` созданы:

- `isAuthenticated` — проверяет `req.session.user`. Если пользователя нет, при GET-запросе выполняется переход на `/login`, а при другом методе (например, ручной POST) возвращается ошибка 401.
- `isAdmin` — проверяет, что пользователь вошёл и его роль `admin`. Если пользователь вошёл, но он не администратор, возвращается **403 Forbidden** и страница `views/403.ejs`.
- `isGuest` — не даёт открыть `/login` и `/register` уже вошедшему пользователю.

Права доступа:

| Действие | Гость | User | Admin |
| --- | --- | --- | --- |
| Просмотр курсов и преподавателей | Да | Да | Да |
| Поиск и фильтрация | Да | Да | Да |
| Просмотр профиля | Нет | Да | Да |
| Просмотр статистики | Нет | Да | Да |
| Добавление, редактирование, удаление курсов | Нет | Нет | Да |
| Добавление, редактирование, удаление преподавателей | Нет | Нет | Да |

Middleware подключены прямо в маршрутах, например:

```js
router.get('/courses/new', isAdmin, controller.showCreateForm);
router.post('/courses', isAdmin, courseRules, controller.addCourse);
router.post('/courses/:id/delete', isAdmin, controller.findCourse, controller.deleteCourse);
router.get('/statistics', isAuthenticated, controller.getStatistics);
```

Поэтому даже если обычный пользователь вручную отправит POST-запрос, он получит 403, а не просто не увидит кнопку.

### Данные пользователя в шаблонах

В `app.js` после подключения сессии добавлен middleware, который записывает `res.locals.currentUser` и `res.locals.isAdmin`. Эти значения доступны во всех EJS-шаблонах. В меню гость видит «Вход» и «Регистрация», вошедший пользователь — своё имя, «Профиль», «Статистика» и «Выход», администратор дополнительно видит «Добавить курс» и «Добавить преподавателя». Кнопки «Изменить» и «Удалить» отображаются только администратору.

### Создание администратора

При регистрации все получают роль `user`. Чтобы получить администратора, нужно зарегистрировать обычного пользователя, изменить роль в базе и войти заново:

```sql
UPDATE "Users" SET role = 'admin' WHERE email = 'admin@example.com';
```

### Валидация

Вся проверка форм вынесена в `middleware/validation.js` и сделана через `express-validator`:

- регистрация — имя, email, пароль, подтверждение пароля;
- вход — email и пароль;
- преподаватель — имя, email, кафедра, учёная степень;
- курс — название, кредиты (целое от 1 до 30), семестр (от 1 до 8), описание, `teacherId`.

Ошибки собираются через `validationResult()` и показываются списком над формой с кодом 400. В контроллере дополнительно проверяется то, для чего нужен запрос к базе: занятый email (код 409) и существование выбранного преподавателя. В формах отключена браузерная проверка (`novalidate`), чтобы было видно, что данные проверяет сервер.

### Централизованная обработка ошибок

Созданы `middleware/notFound.js` (подключается после всех маршрутов) и `middleware/errorHandler.js` (подключается последним). Все операции с базой написаны через `async/await` и `try...catch`, а в `catch` вызывается `next(error)`. Если запись не найдена или ID некорректный, контроллер создаёт ошибку с `status = 404` и тоже передаёт её в `next()`.

| Код | Ситуация |
| --- | --- |
| 400 | Некорректные данные формы |
| 401 | Действие без входа (например, ручной POST) или неверный пароль |
| 403 | Недостаточно прав |
| 404 | Страница, курс или преподаватель не найдены |
| 409 | Email уже зарегистрирован |
| 500 | Внутренняя ошибка сервера (например, нет подключения к базе) |

Пользователю показывается только понятное сообщение. Stack trace, SQL-запросы, параметры подключения и содержимое `.env` на страницу не выводятся, подробности ошибки 500 пишутся только в терминал.

### Логирование

Morgan подключён два раза: `morgan('dev')` выводит запросы в терминал, а второй экземпляр пишет их в файл `logs/requests.log` в формате:

```
POST /login | 302 | 64 ms | 23.11.2026 22:18
GET /profile | 200 | 5 ms | 23.11.2026 22:18
POST /courses | 403 | 1 ms | 23.11.2026 22:19
```

Для даты создан свой token `datetime`.

### Уведомления через WebSocket

Приложение запускается через `http.createServer(app)`, к этому серверу подключён Socket.IO, а объект `io` сохранён через `app.set('io', io)`. Когда администратор добавляет курс, контроллер получает `io` через `req.app.get('io')` и отправляет всем клиентам событие `courseCreated` с названием курса, именем преподавателя и временем добавления.

На каждой странице есть блок «Уведомления» в правом нижнем углу. Файл `public/js/notifications.js` подключается к серверу, слушает событие `courseCreated` и без перезагрузки страницы добавляет сообщение:

```
Добавлен новый курс: Server-side Programming
Преподаватель: Ivan Ivanov
```

Сообщение выделено цветом, имеет кнопку закрытия и само исчезает через 10 секунд.

### Проверка защиты

| Ситуация | Результат |
| --- | --- |
| Гость открывает `/profile` | 302, переход на `/login` |
| User открывает `/courses/new` | 403, страница «Доступ запрещён» |
| User вручную отправляет POST на `/courses` | 403, курс не создаётся |
| User пытается удалить курс | 403, курс не удаляется |
| Неправильный пароль | 401, «Неверный email или пароль» |
| Регистрация существующего email | 409, сообщение над формой |
| Несуществующий ID (`/courses/99999`, `/courses/abc`) | 404 |
| Admin добавляет курс с несуществующим преподавателем | 400, «Выбранный преподаватель не существует» |
| База данных недоступна | 500, «Нет подключения к базе данных» |

Во всех случаях сервер продолжает работать.

## Запуск

1. Запустить PostgreSQL с базой `node_courses`.
2. Указать данные подключения, `SESSION_SECRET` и `BCRYPT_ROUNDS` в файле `.env`.
3. Выполнить:

```bash
npm install
npm start
```

Адрес приложения: `http://localhost:3000`.
